# 报销单发票匹配

## 目标

上传一份报销单，只识别其中的发票号码，再用当前用户的 `invoice_num` 精确查询发票库。匹配过程不修改发票、不修改报销状态，也不按文件名、销售方、金额或商品名称猜测对应关系。

## 流程

1. 左侧菜单进入“报销单匹配”。
2. 上传未加密 PDF。任务进入 Celery，页面轮询识别进度。
3. 原生文字层存在时直接读取票号列；没有文字层时只渲染票号列，使用 Tesseract 英文数字模型识别 8 位或 20 位数字。
4. 识别完成后，后端按当前用户和精确票号匹配发票。
5. 页面展示已找到、未找到、多个候选和待核对结果。低置信度 OCR 号码可直接修正后重新匹配。

6. 所有号码都确认匹配后，可将报销单入库。入库会复制原 PDF 到受管存储，并持久化报销单与发票的关联；后续可从“已入库报销单”打开、下载、添加或移除发票，删除报销单不会删除发票。
7. 已入库报销单中的发票复用系统全局选择集合，支持全选、部分取消、反选、跨左栏保留选择及批量修改报销状态。
8. 输入财务实际到账金额后，后台以分为单位执行 0/1 背包，找到精确金额组合后可一键选中；没有精确组合时不改变当前选择。

当前仅支持 A4 竖版、约 500-650 x 700-900 pt 的浙江大学报销单版式，最多 20 页、每份最多 500 个票号。任务文件存储在受管临时目录，失败后删除；成功且未入库的识别记录保留临时原 PDF，入库时转移到正式报销单存储。识别记录只保留票号、页码、来源和置信度。

## 报销状态与反选

- 报销单页与发票总页共用 `frontend/src/utils/reimbursement.ts` 的状态配色：未报销为灰色、已报销为绿色、报销中为橙色，需换开、被打回和疑似红冲为红色；修改状态后标签颜色随之更新。
- 新增报销状态“被打回”（`rejected`），与“需换开”独立。报销单批量修改、发票列表的单张/批量修改及筛选均可使用；发票详情、邮件内嵌列表和批量打印页显示相同名称。
- 修改状态成功后立即同步报销单表格和全局已选发票，保留当前勾选；接口返回 `updated_count = 0` 也会同步显示，因为该数字仅代表实际发生变化的记录数。失败时不修改显示状态。
- 提交时固定发票 ID、目标状态和所属报销单，等待期间禁用状态提交，避免重复提交或切换报销单后回填到错误对象。手动刷新保留当前报销单，并重新获取其发票状态。
- “反选”只切换当前报销单内的发票：已选变为未选，未选变为已选。其他报销单或发票列表中选择的发票保持不变；空报销单的反选按钮禁用。
- 可以先按实际到账金额选中精确组合并标记“已报销”，再点击“反选”，将剩余发票标记为“被打回”。金额只能提供组合方案，状态仍由用户确认修改。
- 状态存储沿用 `invoices.reimbursement_status` 字符串列，无需数据库迁移。

## 资源与安全

- API 与 Celery worker 使用同一后端镜像；镜像包含 `tesseract-ocr` 与 `tesseract-ocr-eng`。不安装中文语言包，因为当前目标只识别数字票号。
- 每页最多执行一次数字 OCR；Tesseract 设置 `OMP_THREAD_LIMIT=1`。页面任务超时 150 秒，Celery 硬超时 210 秒；单用户最多同时有 3 个任务。
- OCR 只在后台任务执行，不阻塞 API 请求。服务重启后超过 15 分钟仍处于排队/识别中的任务会标记失败并清理临时 PDF。
- 文件先验证 PDF 魔数、页数和版式；路径使用用户和 UUID 组成，不接受用户提供的路径。
- 所有读取、匹配、删除接口都按当前用户过滤；匹配响应只返回必要的发票摘要，不返回文件路径、OCR 原文或其他敏感字段。
